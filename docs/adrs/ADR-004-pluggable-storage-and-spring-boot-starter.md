# ADR-004: Pluggable Storage and Spring Boot Starter

**Date:** 2026-07-04  
**Status:** Superseded by ADR-007 and ADR-009  
**Deciders:** Project maintainers

## Context

> The provider-neutral boundaries remain valid, but ADR-007 supersedes the two-dependency consumer packaging decision and ADR-009 supersedes the low-level service as the primary Spring developer API.

Blob Helper should support S3, Azure Blob Storage, local filesystem storage, and future providers while exposing one storage-neutral service API to applications.

## Decision

Applications interact with `BlobDeduplicationService`, not provider-specific APIs or controllers. The Spring Boot starter owns properties binding and conditional provider wiring. Provider SDK code lives only in provider modules. Local storage is provided for tests and development without cloud credentials.

## Invariants (from Q2)

- [ ] Public service APIs must remain storage-neutral.
- [ ] Provider-specific settings must stay out of `dedup4j-core`.
- [ ] The starter must wire exactly one configured provider.
- [ ] Local storage must support deterministic tests without cloud credentials.
- [ ] The starter must not expose REST controllers.
- [ ] No public URLs are generated by default.

## Architectural Ownership (from Q3)

| Concern | Owner |
|---------|-------|
| Provider-neutral contracts | `dedup4j-core` |
| Auto-configuration and properties | `blob-helper-spring-boot-starter` |
| S3 SDK code | `dedup4j-storage-s3` |
| Azure SDK code | `blob-helper-storage-azure` |
| Local filesystem storage | `dedup4j-storage-local` |

**Explicitly excluded layers:** `dedup4j-core` and the starter must not contain provider SDK implementation code.

## Consequences

**Positive:**
- Consumers can change providers by dependency/configuration changes.
- Core tests remain fast and deterministic.
- Applications keep their own REST API shape.

**Negative / Trade-offs:**
- Provider modules need separate test strategies.
- Auto-configuration must fail clearly for missing or ambiguous providers.

**Risks if violated:**
- Business logic may depend on a provider SDK.
- Starter may become too opinionated for reusable library use.
- Tests may require cloud credentials unnecessarily.

## Rejected Alternatives

### Alternative A: Built-in upload controllers
- Why considered: faster demo experience.
- Why rejected: violates the requirement that each app owns its REST shape and logical asset model.

### Alternative B: Single module with all providers
- Why considered: simpler Maven setup.
- Why rejected: violates provider isolation and forces unused SDK dependencies on consumers.
